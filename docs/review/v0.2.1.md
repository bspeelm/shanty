# Review packet — v0.2.1

Two CI jobs were added that run on the systems the packages are installed on.
Both went red on their first run, and both were right. Everything in this
release is what they found.

## What changed

**shanty resolves the same four directories on macOS as on Linux.** `Discover`
took two of the four from `os.UserConfigDir` and `os.UserCacheDir` and the
other two from the environment. On Linux the standard library reads the XDG
variables, so the split was invisible. On macOS it answers `~/Library/
Application Support` and `~/Library/Caches` and ignores `XDG_CONFIG_HOME` and
`XDG_CACHE_HOME` entirely. shanty was half one convention and half the other on
that platform, and the environment variables it documents did not work there.

ADR-012 records the decision and the argument that settled it, which is fish:
the fish completion is written beside fish's own configuration, and fish
follows XDG on macOS. A macOS-native table would have had to except fish from
itself.

**This moves where an existing macOS installation keeps its files.** See the
upgrade note below; it is the one user-visible break in this release.

**The Homebrew cask installs completions.** A cask installs a binary and
nothing else unless told otherwise, so Homebrew was the one package route that
placed none, while the install page claimed every route but `go install` did.
The archive now carries the three generated files and the cask declares a
stanza for each.

**The source rpm stops when git lists no files.** `git ls-files | tar -cf - -T -`
reports tar's exit status. A git that refused to read the repository produced
an empty tarball, a source rpm that built cleanly around an empty directory,
and a failure two steps later at `go build` with no `go.mod`. The refusal was
ownership: the build can run as a different user from the one that owns the
checkout. This was reachable from Copr, not only from CI.

**Two CI jobs.** `macos` runs the suite on a macOS runner and asserts the
doctor reports every check. `rpm` builds the source rpm exactly as Copr does,
rebuilds it, installs it in a Fedora container, checks that mpv came with it
and that the shipped completions are the ones the binary writes, then removes
it and checks the binary is gone.

## Upgrading on macOS

A v0.2.0 installation keeps its configuration in `~/Library/Application
Support/shanty` and its cache in `~/Library/Caches/shanty`. v0.2.1 looks in
`~/.config/shanty` and `~/.cache/shanty` and does not migrate the old ones,
which means it asks for a server and a credential again and leaves the old
directory in place.

To keep an existing setup, after upgrading:

```sh
mkdir -p ~/.config
mv "$HOME/Library/Application Support/shanty" ~/.config/shanty
rm -rf "$HOME/Library/Caches/shanty"
```

To start clean instead, run `shanty uninstall` **before** upgrading. It removes
the four directories as the running binary resolves them, so the v0.2.0 binary
is the one that knows where they are.

`~/.local/state/shanty` needs nothing. State was already resolved from the
environment and was in the right place.

Migrating automatically was refused. It is a permanent platform-specific code
path, in a program with forty lines left against §0's code budget, for one
release that documented macOS as unverified.

Linux is unaffected in every respect.

## The five answers

Unchanged from v0.2.0 except as follows. `docs/review/v0.2.0.md` has them in
full.

**Paths written, and what permits each.** The same eight paths, with the same
modes and the same writers. What changed is where four of them resolve to on
macOS, which is now what the table already said.

**How bytes enter, and the gate on each.** Unchanged.

**External processes and their environment.** Unchanged.

**Deletion paths.** Unchanged in code. One consequence is new and is the reason
for the upgrade note: `uninstall` removes the directories the running binary
resolves, so a v0.2.1 binary will not remove a v0.2.0 macOS installation.

**Which check proves each claim.** The claims are the same and three jobs now
prove more of them. `macos` runs the isolation suite, which asserts the write
set, on the platform that was breaking it. `rpm` proves the package installs
and removes cleanly. The `packages` job reads the generated cask for its four
stanzas and checks that both darwin archives carry every file it names.

## Where to look hardest

**`Discover` in `internal/config/paths.go`.** Four directories, one helper,
`xdgDir`, for all of them. The thing to satisfy yourself about is that no
caller anywhere resolves a directory another way, because that is exactly the
defect being fixed and it survived a year by being invisible on one platform.

**`.copr/Makefile`.** The guard is `test -s` on the file list and `test -f` on
`go.mod` in the unpacked tree. A pipeline whose exit status comes from the last
command is the general shape of this bug, and the recipe still has pipelines in
it.

**The completion paths.** Three routes place these now and they disagree about
zsh: dnf, apt and Homebrew place all three, while `shanty completions install`
places bash and fish and leaves zsh to be put somewhere root owns. The install
page says so; check that it still matches what the code does.

## What was not verified

Everything in the v0.2.0 packet still applies. The endpoints v0.2 added have
run only against the fake in this repository.

**No macOS binary from a release has been run by CI.** The `macos` job builds
and tests from source. What a released, notarised-by-nobody tarball does on a
Mac is still only known from one person installing the cask by hand.

**The upgrade path in this document has not been executed.** The commands are
`mv` and `rm -rf` against paths this release stops using, and no test covers
them because no test can: there is no v0.2.0 macOS installation in CI to
upgrade.

**The cask's completion stanzas have not been installed by brew.** CI asserts
that the cask declares them and that the archive carries the files. Whether
Homebrew places them where the three shells read is the claim resting on
Homebrew behaving as documented.
