# Review packet — v0.3.3

v0.3.2 was released as the fix for nine advisories and did not contain it.
This is that release, and the check that stops it happening again.

## What happened

v0.3.2 bumped `go.mod` and ten `go-version` pins from 1.25 to `'1.26'`, and
was published built with **go1.26.8**. The advisories are fixed in go1.26.9.

```
$ go version ./shanty          # the published v0.3.2 tarball
./shanty: go1.26.8
$ govulncheck -mode=binary ./shanty
Your code is affected by 12 vulnerabilities from the Go standard library.
```

`setup-go` matches a version *spec* against what the runner already has:

```
Setup go version spec 1.26
Successfully set up Go version 1.26
go version go1.26.8 linux/amd64
```

It reported success. goreleaser reported success. The release reported success.

**The rpm was never affected.** Fedora ships golang 1.26.9, so dnf and Copr
built with the fix. The tarballs, the deb and the Homebrew cask did not, which
means the two channels disagreed about what v0.3.2 was.

## Why it was not caught

The fix was verified by running `GOTOOLCHAIN=go1.26.9 govulncheck` on a machine
that had 1.26.9 installed. That proves the fix works. It proves nothing about
what CI builds with, and those are different questions.

The v0.3.1 packet states the gap in as many words — *"the released binary is
built by CI with `go-version: 1.26`, which is the same floor and not the same
toolchain"*. The sentence was written and not acted on. A known gap that is
only ever written down is indistinguishable from one nobody noticed.

## What changed

**`go.mod` names the toolchain.** `toolchain go1.26.9`, so the requirement
travels with the module rather than being repeated across ten workflow pins.

**The pins name the patch version.** `go-version: '1.26.9'`.

**Neither of those is the fix**, and both can fail quietly again. On the
machine this was prepared on `GOTOOLCHAIN=local` makes the toolchain directive
advisory, and `go build` produced a 1.26.8 binary without complaining.

The fix is a guard in **both** workflows that compares the compiler it is about
to build with against what `go.mod` asks for:

| go.mod asks | built with | |
|---|---|---|
| 1.26.9 | 1.26.8 | stops — the case that shipped |
| 1.26.9 | 1.25.14 | stops |
| 1.26.9 | 1.26.9 | builds |
| 1.26.9 | 1.26.10 | builds |
| 1.26.9 | 1.27.0 | builds |

In `release.yml` it runs **before goreleaser**, so a short toolchain stops the
release instead of publishing one. In `ci.yml` it runs on every pull request,
where finding out is free. It is a check on the artifact's own provenance
rather than on an intention, which is the distinction v0.3.2 turned on.

## The five answers

Unchanged from v0.3.1. No path is written, no byte enters, no process is run
and no deletion path is touched.

## What was not verified

Everything in the v0.3.0 packet still applies: iTerm2 has never drawn a cover,
sixel is absent, and six of twenty-two endpoints have run against a real server.

**The guard has never stopped a real release.** Its comparison is checked
against five pairs including the one that shipped, and it has run green in CI.
It has not been observed refusing a build, because doing that honestly means
publishing a bad one.

## The pattern

This is the fourth time in this project that something was arranged, looked
arranged, and did nothing: a doctor check for a terminal that could not draw
pictures, levelling that is silent over an untagged library, a weekly check
that notified nobody, and now a release that reported success while shipping
the thing it was cut to remove.

The common shape is that success and failure looked identical from outside. The
answer each time was the same: check the artifact rather than the intention.
