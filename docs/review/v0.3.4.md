# Review packet — v0.3.4

A track that would not play was reported as playing. This is the fix, what mpv
had to say about it that was being thrown away, and a doctor check that finds
the fault without waiting for an album to go silent.

## What happened

A track loaded, the status row named it, the position stayed at 0:00, and
nothing else happened. No message, no advance, no way on but quitting. Every
track after it behaved the same way until shanty was restarted.

mpv was not at fault and neither was the server: the audio output refused the
sample rate and never started. What shanty did wrong was report that state as
playback.

```
loadfile        -> success
start-file      -> arrives
file-loaded     -> arrives
playback-restart-> arrives
time-pos        -> 0.0, and never again
```

There is no `end-file`. `playerSaid` acts on `end-file` with reason `eof` and
on nothing else, which is correct for a skip or a seek and leaves this failure
with no event to act on at all.

## What changed

**A watch, because there is no event.** One starts with each track and asks,
after `stallGrace`, whether the position has moved. Not moved and not paused is
reported. Playback that is moving re-arms the watch, so a track that stops
halfway is caught too. A paused track re-arms rather than reporting. Each watch
is numbered, so an answer about a track the queue has already passed is dropped
instead of naming the wrong one.

**mpv's own account, which was never reaching anything.** The issue said to
give mpv's stderr a destination. Measuring it found the premise wrong: mpv
writes its messages, errors included, to **standard output** and leaves
standard error empty, and `Start` was not wiring standard output at all. The
field was named for a stream mpv does not use.

```
$ mpv ... >out.txt 2>err.txt     # a stream that fails to open
out.txt: [ytdl_hook] ERROR: Unsupported URL: <the stream URL>
err.txt: (empty)
```

`Options.Stderr` is now `Options.Diagnostics`, wired to both streams.
`--term-status-msg=` silences the position line mpv otherwise repeats several
times a second over the top of anything worth reading.

**Nothing is written to disk.** The line above carries the credential, because
a stream URL is how shanty asks for audio. Every URL has its query removed
before a line is kept, the lines are held a few at a time in memory, and §8 is
unchanged: still four directories and nothing else.

**`doctor` exercises the output.** `audio-output` gives mpv one second of
silence it generates itself and waits for it to finish. Nothing is heard, no
file is read, nothing is created. It asks at **44.1 kHz** on purpose: that is
the rate most music is in and the rate an output is most likely to refuse, so
the same check at 48 kHz would pass on a machine where half a library is
silent. No audio device at all is a warning rather than a failure.

## The five answers

Unchanged from v0.3.0 in four of them. No new path is written, no new process
is run beyond the one `doctor` starts and stops, and no deletion path is
touched.

**What enters.** One new byte stream: what mpv writes about itself. It is
treated as hostile text — its URLs have their queries removed before anything
is kept, and it reaches the screen through the same `Sanitise` every other
message does (ADR-013).

**Which check proves each claim.** New:

| claim | proof |
|---|---|
| a track that never plays is reported | `TestATrackThatNeverPlaysIsReported` |
| a track that is playing is not | `TestATrackThatIsPlayingIsNotReportedAsStalled` |
| a paused track is not | `TestAPausedTrackIsNotReportedAsStalled` |
| a watch from a passed track names nobody | `TestAStallWatchFromATrackAlreadyPassedIsIgnored` |
| what mpv says reaches shanty at all | `TestWhatMpvSaysReachesTheCaller` |
| what mpv says never carries the credential | `TestWhatMpvSaidNeverCarriesTheCredential` |
| mpv's output cannot grow without bound | `TestMpvsStatusLineDoesNotGrowInMemory` |
| the doctor reports an output that will not start | `TestTheDoctorReportsAnAudioOutputThatNeverStarts` |
| the doctor still creates nothing | `TestDoctorCreatesNothing` |

Every one was confirmed to bite by planting the bug it catches, including
wiring only standard error — the bug that was actually there.

## What was not verified

Everything in the v0.3.0 packet still applies: iTerm2 has never drawn a cover,
sixel is absent, and six of twenty-two endpoints have run against a real
server.

**`audio-output` has never failed against real hardware.** Its passing path is
verified on a real machine with a real DAC. Its failing path is verified only
against a stubbed command. The fault that prompted it turned out to be
state-dependent — it needs the audio graph free to change rate — and could not
be put back on demand once it was fixed. Three attempts to reproduce it all
passed, which is how the state-dependence was found.

**`stallGrace` is a guess.** Twelve seconds is longer than any start observed
here by a factor of ten, and a server slow enough to beat it will produce a
message that is wrong. The position is the only signal available; there is no
event, and mpv does not distinguish buffering from an output that will not
start.

## The budget script counted vendored panics

`make check` failed on macOS and passed in CI. The budget it failed was
`panic(` in non-test code, which is zero, and it reported 46.

The 46 are all in `vendor/`. The script searched from the repository root and
removed vendored files afterwards:

```
grep -rn 'panic(' --include='*.go' . | grep -v '_test.go' | grep -v '^\./vendor/'
```

GNU grep writes `./vendor/golang.org/...` for a recursive search and the filter
removes it. BSD grep writes `vendor/golang.org/...` with no leading `./`, so
the filter matched nothing and every vendored panic was counted. The same
search scoped to this project's own files has always returned 0.

Three places shared the pattern. Two counted panics. The third names any file
mentioning `InsecureSkipVerify`, which is how ADR-004 is asserted; it reported
nothing wrong only because no vendored module contains that identifier. It was
a trap rather than a failure, and it is fixed with the other two.

**What changed.** The files are named by `find`, which writes a path the same
way on every platform, and the counts read that list instead of filtering
grep's own output. `find` with `-not -path './vendor/*'` is how the other
counts in the script already select files.

**What proves it.** `TestTheBudgetScriptDoesNotCountVendoredPanics` counts the
lines in `vendor/` that contain `panic(` and fails if there are none, then runs
the script and requires a reported zero. Asserting the zero alone would pass
against an empty vendor directory, which is the state that hides this fault.

**What is not proved.** The `InsecureSkipVerify` site has no test. No vendored
module contains the identifier, so an assertion about it would hold whether the
exclusion worked or not. Naming the identifier in a test file also trips the
check, which is correct behaviour and was found by doing it.

## The pattern

This is the fifth time something was arranged, looked arranged, and did
nothing. The first four are in the v0.3.3 packet. This one is the same shape
three times over in one release: a player that reported a dead track as
playing, a field called `Stderr` wired to a stream its process never writes to,
and a filter that removed vendored files from a count without matching any of
them. All three looked connected. None was, and nothing said so.

The answer is the one the previous four arrived at: check the artifact rather
than the intention. `TestWhatMpvSaysReachesTheCaller` exists because a field
that looks wired is not evidence that anything comes out of it, and
`TestTheBudgetScriptDoesNotCountVendoredPanics` counts what `vendor/` holds
before it will believe a zero.
