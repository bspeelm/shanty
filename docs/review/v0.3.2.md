# Review packet — v0.3.2

A security release and nothing else. One commit, thirteen lines, no behaviour
changed.

## What changed

**shanty is built with Go 1.26.9.** v0.3.1 was built with 1.25.14, which
`govulncheck` reports nine reachable vulnerabilities against:

| | in | |
|---|---|---|
| GO-2026-6617 | `net/http` | HTTP/2 crash from an HPACK encoder race |
| GO-2026-6613 | `net/http` | HTTP/1 desynchronisation after a 2xx CONNECT |
| GO-2026-6612 | `net/http` | double flow control refund on HTTP/2 streams |
| GO-2026-6611 | `net/http` | CPU exhaustion from repeated window changes |
| GO-2026-6610 | `net/http` | malformed framing headers accepted |
| GO-2026-6608 | `mime/multipart` | memory limit bypass parsing MIME headers |
| GO-2026-6607 | `crypto/tls` | malformed ECH outer extension references |
| GO-2026-6605 | `net/http` | HTTP/1 desynchronisation after a CONNECT rejection |
| GO-2026-6603 | `net/http` | HTTP/2 memory exhaustion via Trailer headers |

All nine are fixed in go1.26.9. None is in a dependency: the report says
everything there is current.

Reachability is reported rather than assumed. Traces run through
`subsonic.Client.CoverArt` and `subsonic.Client.get`, which is the path of
every request shanty makes.

## What a reviewer should weigh first

### Most of these are server-side bugs in a program with no server

Seven of the nine are in `net/http`, and several describe a *server* being
crashed, desynchronised or exhausted by a hostile client. shanty runs no
server. `govulncheck` reports them because the vulnerable symbols are reachable
from code that is linked in — `httptest.NewServer` in the fake, and the shared
HTTP/1 and HTTP/2 machinery the client half uses.

That is a reason to be precise about the risk, not a reason to discount it.
The client-side ones are real for shanty: an HTTP/1 desynchronisation after a
CONNECT rejection and a transport accepting malformed framing headers are both
things a server, or something between shanty and a server, can do to it.
`internal/subsonic` is the only package that talks to the network and every one
of these is on that path.

### Twelve pins, two of which a search does not find

`go.mod`, ten `go-version` lines, **the container image the buildroot job
compiles in**, and **`BuildRequires` in the rpm spec**. The last two are not
found by searching for `go-version`. They were missed when this was done for
1.25 and caught by the buildroot job failing, which is what that job is for.

### 1.26 rather than 1.27

Go 1.27.2 is also released. 1.26.9 is the version the advisories name, it is
the latest 1.26.x, and it clears all nine. A lower floor is one the Fedora
toolchain that compiles the rpm is likelier to meet, and that build is the one
that broke last time.

## The five answers

Unchanged from v0.3.1 in every respect. No path is written, no byte enters, no
process is run and no deletion path is touched that was not already there.

## What was not verified

Everything in the v0.3.0 and v0.3.1 packets still applies: iTerm2 has never
drawn a cover, sixel is absent, and six of twenty-two endpoints have run
against a real server.

**The advisories are proven fixed against go1.26.9 specifically.** The Go
installed on the machine this was prepared on is 1.26.8 — before the fix — so
verifying against whatever was present would have proved nothing. It was run as
`GOTOOLCHAIN=go1.26.9`, which is the version CI's `go-version: '1.26'` resolves
to, and the result is unqualified: nine before, none after.

## The weekly check

This release exists because the check found the advisories on **its first
unattended run**. Until now it had only ever been triggered by hand.

What that proves: it runs on schedule, finds reachable vulnerabilities in the
standard library, opens an issue and notifies somebody. What it still does not
prove is the quiet path — that a week which finds nothing new stays silent
rather than commenting. That remains untested until a week passes with no
change.
