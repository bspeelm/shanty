# Review packet — v0.3.1

A security release. Seven advisories against the standard library shanty was
built with, and two keys that make playlists work the way somebody expects.

## What changed

**shanty is built with Go 1.25.** v0.3.0 was built with 1.24.13, which
`govulncheck` reports seven reachable vulnerabilities against:

| | in | fixed in |
|---|---|---|
| GO-2026-6218 | `net/url` | go1.25.13 |
| GO-2026-6090 | `crypto/tls` | go1.25.13 |
| GO-2026-6089 | `net/http` | go1.25.13 |
| GO-2026-5972 | `encoding/asn1` | go1.25.13 |
| GO-2026-5856 | `crypto/tls` | go1.25.12 |
| GO-2026-5039 | `net/textproto` | go1.25.11 |
| GO-2026-5037 | `crypto/x509` | 1.25.x |

None are in a dependency. Reachability is reported rather than assumed: one
trace runs `subsonic.Client.CoverArt` into `http.Client.Do` into
`url.URL.Parse`, which is the path every cover art request takes.

`golang.org/x/sys` moves to v0.44.0 for an eighth, an integer overflow in a
Windows call. shanty builds for linux and darwin, so that code is in nothing
that ships. It is bumped so that the weekly report reads clean, because a
report that is permanently not clean is one nobody reads.

**`e` and `r` act on the playlist on screen.** Adding to a playlist meant
typing its name with that playlist already open. Removing meant entering edit
mode first.

## What a reviewer should weigh first

### Removing a track is by position, and the position now travels with it

The intent carried only a track identifier, and the app resolved it to the
**last** occurrence of that identifier. From the library that is right: the
position in the playlist is not on screen to point at, and `r` after `a` should
take back out what was just put in.

From the playlist itself it was wrong. **A playlist may hold the same track
twice, and taking out the first would have taken out the second**, with nothing
on screen showing which had gone.

A position that no longer holds the track it held is **refused**. Between the
screen being drawn and the key being pressed the playlist can change, and
removing whatever is there now would delete something nobody chose. It is the
one mistake in this feature that cannot be undone from inside shanty.

### The weekly dependency check told nobody

It opened one issue and rewrote its body every week after. **Editing an issue
body notifies nobody** — not the author, not a watcher, not the assignee. A
vulnerability found in week six would have been written down and never read.

It is assigned when opened, compares each week against the last ignoring the
date, and comments only when something differs. A week that found the same
thing writes nothing at all.

It had also never run. Its first attempt failed on a label that had never been
created, which would have failed identically every Monday. The label is made by
the run now.

**The seven advisories above are what its first working run found.** The check
and the finding arrived together, which is the argument for the check.

## The five answers

Unchanged from v0.3.0 in every respect. No new path is written, no new byte
enters, no new process is run, and no deletion path is added — the one that
existed is narrowed.

**Which check proves each claim.** New:

| claim | proof |
|---|---|
| removing takes the track pointed at | `TestRemovingTakesTheTrackPointedAtNotAnotherCopy` |
| a playlist that moved is not removed from | `TestRemovingRefusesWhenThePlaylistMovedUnderneath` |
| `e` starts from the playlist on screen | `TestEditingStartsFromThePlaylistOnScreen` |
| nothing is claimed before the server has done it | the absence of a status until `PlaylistLoaded` |

## What was not verified

Everything in the v0.3.0 packet still applies: iTerm2 has never drawn a cover,
sixel is absent, and six of twenty-two endpoints have run against a real
server.

**The weekly check has run twice by hand and never on its schedule.** Its first
scheduled run is the Monday after this release. What is proven is that it
opens, assigns and finds things; what is not is that a week with no change is
silent in the way it was written to be.

**The advisories are proven fixed on this machine**, by running `govulncheck`
against the bumped toolchain: seven before, none after, and the second result
unqualified rather than "none reachable". The released binary is built by CI
with `go-version: 1.25`, which is the same floor and not the same toolchain.
