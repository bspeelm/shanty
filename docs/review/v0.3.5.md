# Review packet — v0.3.5

A security release. The toolchain moves from Go 1.26.9 to Go 1.26.11 and no
behaviour changes. It is v0.3.4 with that one change, cut from the v0.3.4 tag
and not from `main`.

## What changed

**shanty is built with Go 1.26.11.** v0.3.4 was built with 1.26.9, which
`govulncheck` reports two reachable vulnerabilities against:

| | in | | fixed in |
|---|---|---|---|
| GO-2026-6809 | `crypto/x509` | compromised intermediate certificates are not distrusted | 1.26.10 |
| GO-2026-6859 | `net/http` | HTTP/1 server crash from a `MaxBytesReader` header race | 1.26.11 |

Neither is in a dependency. The scan reports no vulnerability in any module
shanty requires.

The change is the `toolchain` line in `go.mod` and the ten `go-version`
pins in the three workflows. The container image the buildroot job compiles
in is `golang:1.26-alpine`, which follows the latest 1.26 patch release and
is unchanged.

## What a reviewer should weigh first

### One of the two applies to a client

GO-2026-6809 is in certificate verification, which shanty does on every
HTTPS connection to a server. The trace runs through
`subsonic.Client.CoverArt`.

GO-2026-6859 describes a server being crashed. shanty runs no server. The
scan reports it because `httptest.NewServer` in the fake server is linked
into the tests and the symbols are shared with the client.

### The rpm on Fedora 43 and 44 gets one fix of the two

The rpm is compiled by the Go that Fedora ships, not by the toolchain
`go.mod` names. On the day this was prepared the repositories held:

| Fedora | golang | GO-2026-6809 | GO-2026-6859 |
|---|---|---|---|
| 43 | 1.26.10 | fixed | present |
| 44 | 1.26.10 | fixed | present |
| 45 | 1.27.4 | fixed | fixed |

The spec still requires `golang >= 1.26`. Requiring 1.26.11 would stop the
Fedora 43 and 44 builds until Fedora ships it, and the advisory those builds
would be held for is the server-side one. The tarballs, the deb and the cask
are built by the release workflow with 1.26.11.

## How it was checked

The scan was run against this tree with each toolchain:

```
$ GOTOOLCHAIN=go1.26.9  govulncheck ./...
Your code is affected by 2 vulnerabilities from the Go standard library.
$ GOTOOLCHAIN=go1.26.10 govulncheck ./...
Your code is affected by 1 vulnerability from the Go standard library.
$ GOTOOLCHAIN=go1.26.11 govulncheck ./...
No vulnerabilities found.
```

`make check` passes on this tree.

The release workflow compares the compiler it builds with against the
`toolchain` line in `go.mod` before goreleaser runs, and stops if the
compiler is older.

## The five answers

Unchanged from v0.3.4. No path is written, no byte enters, no process is run
and no deletion path is touched that was not already there.

## What was not verified

Everything in the v0.3.4 packet still applies.

**The published binaries have not been scanned.** The scan above is of the
source with the toolchain selected by hand. Running
`govulncheck -mode=binary` on the published v0.3.5 tarball is the check that
the release was built with 1.26.11, and it can only be run after the release
exists.

**The Fedora versions in the table are a reading on one day.** A Copr build
uses whatever the build root holds when it runs.

**Fedora 45 has had no rpm before this release.** The Copr project had no
Fedora 45 build root for v0.3.4. Whether this release builds and installs
there is known only once Copr has built it.
